# STM32U575 / STM32U585 — the `stm32u575` and `stm32u585` machines

Consumed by: `machines/stm32u575.machine`, `machines/stm32u585.machine`,
`scripts/gen-stm32u5-machines.py`, `src/dev/stm32/`, `src/cpu/arm/v7m`.

Two real parts, one die. The **STM32U575ZIT6Q** is the microcontroller on ST's
NUCLEO-U575ZI-Q; the **STM32U585AII6Q**, on the B-U585I-IOT02A Discovery kit, is
the same chip with its crypto blocks bonded out. Both are a Cortex-M33 at up to
160 MHz with FPv5-SP-D16 and the DSP extension, 2 MiB of dual-bank flash and
768 KiB of SRAM.

```sh
rsemu run stm32u575 --media firmware=app.bin
rsemu run stm32u585 --media firmware=app.bin
```

The firmware image is loaded at `0x08000000` and USART1 — the ST-LINK virtual
COM port on both boards — is the terminal.

The two machine files are generated by `scripts/gen-stm32u5-machines.py`,
because a `.machine` file has no include the catalog can resolve and the parts
differ only in the HASH unit. Edit the script and rerun it; do not edit the
files by hand.

## TrustZone is off

The silicon has TrustZone. The option bit that enables it, `TZEN`, is clear out
of the factory, and that is the configuration modelled: everything is
non-secure, firmware uses the non-secure aliases (flash at `0x08000000`, SRAM
at `0x20000000`, peripherals at `0x40000000`), and the core is an Armv8-M
Mainline core **without the Security Extension**. The secure aliases at
`0x0c000000`, `0x30000000` and `0x50000000` are unmapped, `st.flash` refuses an
`optr` with `TZEN` set, and the SAU reads as zero. A `TZEN = 1` part — secure
boot, the GTZC, secure/non-secure banking in every peripheral — is a large
separate piece of work.

## Booting

A U5 has **nothing at address zero**. Where an F4 aliases its boot memory at
`0x00000000`, a U5 starts the core with `VTOR` already pointing at the boot
address: `NSBOOTADD0`, `0x08000000` from the factory. The core's `vtor`
property is that reset value, and every reset — cold, `SYSRESETREQ`, or a
watchdog — fetches the initial `SP` and `PC` from it.

## The clock tree is live

This is the first board in the tree whose RCC drives the scheduler. It comes
out of reset on **MSIS at 4 MHz**, as the part does, and runs at whatever the
firmware programs PLL1 to: 160 MHz for every Cube example. The `clock` objects
in the machine file (`sysclk`, `hclk`, `pclk1`–`pclk3`, `timclk1`, `timclk2`)
are the nodes of that tree, and `st.rcc` re-rates them
([`../techniques/clock-control.md`](../techniques/clock-control.md)). Every
internal source is an exact ratio of the declared 16 MHz HSE; the physical
independence of the RC oscillators is not modelled.

The **peripheral clocks are gated**, too: every peripheral whose enable bit
resets to zero has `rcc.<bus>en<bit> -> <dev>.enable` and the matching reset
wire, so a driver that forgets `__HAL_RCC_xxx_CLK_ENABLE()` talks to a dead
block, exactly as on the silicon. `tests/stm32u5_board.rs` proves it.

## Proof

- `tests/stm32u5_board.rs` — always runs: boot through `VTOR`, USART1 output,
  the clock gate, the signature block, the U585's HASH unit.
- `tests/stm32u5_hal.rs` — **ST's own HAL**, built by
  `scripts/fetch-testdata.sh stm32u5-hal` from pinned commits with
  `arm-none-eabi-gcc` and our app in `tests/fixtures/stm32u5-hal/`. It runs
  `HAL_Init`, the full PWR + RCC configuration to 160 MHz, the ICACHE,
  `HAL_Delay`, GPIO, an EXTI interrupt, ten TIM6 interrupts, CRC, the RNG, a
  float square root, C11 acquire/release atomics (LDA/STL, LDAEX/STLEX),
  `MSPLIM`, a flash page erase and quad-word program, and on the U585 a SHA-256
  — and checks every result. Run it with
  `RSEMU_STM32U5_HAL_DIR=testdata/stm32u5-hal cargo test --release --test stm32u5_hal`.

Getting the HAL through found five defects in the shared v7-M core, all of
which the `stm32f407` board had too: the wide conditional branch offset,
`VLDR`/`VSTR`/`VPUSH` of D registers being UNDEFINED on a single-precision
FPU, the core never publishing its position to the scheduler mid-quantum (so a
register-polling loop with an iteration budget timed out), a tail-chained
handler inheriting a clobbered `LR`, and a level-sensitive interrupt pending
again while its own handler ran.

## What is not modelled, stated plainly

- **TrustZone**, above, and everything that hangs off it: GTZC, the secure
  register banks, `SAES`.
- **GPDMA1 and LPDMA1.** The U5's DMA controllers are a new design (linked
  lists, per-channel FIFOs) that `st.dma` does not cover; their addresses are
  unmapped and no peripheral drives a request.
- **The RTC and TAMP.** The U5 RTC is the newer layout (`ICSR`, `SR`/`MISR`/
  `SCR`, tamper split out) and `st.rtc` is the F4/L4 one; unmapped rather than
  wrong.
- **SYSCFG**, the ADCs, DACs, comparators, op-amps, I²C, SPI, OCTOSPI,
  SDMMC, FDCAN, USB OTG, UCPD, SAI, MDF/ADF, DCMI, DMA2D, CORDIC, FMAC, FMC,
  LPTIMs, TSC, RAMCFG, and on the U585 AES/SAES/PKA/OTFDEC. Several have
  models in the tree for other families (`stm32.spi`, `stm32.octospi`,
  `stm32.sdmmc`, `st.i2c-v2`); placing them needs their U5 deltas checked first.
  An access to any of these addresses is a BusFault.
- **Timer interconnect.** `ITRx` routing differs from the F4's and is not
  wired.
- **The package word reads zero.** Its encoding was not checked against
  RM0456, and a blank value is better than a guessed one.
- **Low-power modes** (Stop 0–3, Standby, Shutdown) and wake-up are register
  storage only.
